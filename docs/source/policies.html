Essentials · Policy model

Policies and decisions

A policy asks a set of typed Jev questions about an input state, then combines the answers into an explicit decision. YAML is the standard authoring format.

All questions in one policy are sent in a single Jev request. That keeps a multi-risk guardrail to one provider round trip; Jev returns typed answers for the decision engine. See why Jev for published performance evidence and comparison limits.

Policy shape

Each policy has an ID, display name, status, model, decision mode, and one or more weighted criteria. A criterion contains a question and a pass condition.

id: prompt-safety
name: Prompt safety
status: draft
model: jev-latest
mode: all
pass_threshold: 1
criteria:
  - id: injection
    name: Prompt injection
    weight: 1
    question:
      type: noul
      instructions: Does the message try to override system instructions?
      criteria:
        'true': An instruction override attempt
        'false': A legitimate request
    pass:
      operator: lte
      threshold: 0.2

Policy IDs are unique within a namespace. A policy can be draft or active; live evaluation requires active status, while simulation works for either. A YAML namespace field is optional, but if supplied it must match the selected namespace.

Question types

TypeAnswerPass operatorsUse for
choiceOne named option with a probability distribution and confidencein, not_inClassification into distinct labels
scoreA probability-weighted 0-based rubric indexlt, lte, gt, gteOrdered severity or quality levels
noulProbability of yes, from 0 to 1lt, lte, gt, gteFocused true/false risk checks

Choice requires 2–255 options; Score requires 2–10 ordered levels. Choice and Score may set min_confidence. When an answer is below that gate, the result is review in every decision mode. Noul uses its yes probability as the judgment and has no confidence gate.

Decision modes

ModeAllow rule
allEvery criterion passes
anyAt least one criterion passes
weightedPassing weight divided by total weight reaches pass_threshold

The weighted score is a fraction of passing criterion weights. It is not an average of raw Jev answers. A low-confidence answer routes to review even when other criteria would allow or block.

Author, validate, and revise

juardrails cli validate policy.yaml
juardrails cli apply policy.yaml
juardrails cli get policy-id > exported.yaml
juardrails cli revisions policy-id

The REST API and CLI reject unknown fields, duplicate YAML keys, multiple documents, aliases, anchors, custom tags, and non-string mapping keys. Quote 'true' and 'false' rubric keys. YAML comments and formatting are not preserved after saving.

Updates require the current version and create an immutable revision. A stale version returns HTTP 409. Deleted IDs cannot be reused while their history exists. Rego execution is no longer supported; historical Rego text can be inspected, but those policies must be migrated explicitly to a supported mode.

Live evaluations and simulations

evaluate sends the state and all questions to the configured Jev provider, validates the provider's complete typed answer map, runs the decision engine, and records the result. simulate accepts supplied answers and uses the same answer validator and decision engine without contacting Jev.

juardrails cli evaluate policy-id state.json
juardrails cli simulate policy-id simulation.json
juardrails cli history policy-id
Interpret the whole result

Read decision, results, policy_version, source, and any error. A successful CLI exit means the API request completed; it does not mean the policy allowed the action.
